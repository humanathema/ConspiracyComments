## 1. Back-translation paraphrase pipeline — built, hardened, run at full scale

`src/generate_backtranslation_paraphrase.py` + `src/clean_reddit_markdown.py`. Goal: generate meaning-preserving rewordings of human-labeled rows (English→German→English via MarianMT) to test whether the classifier's predictions are stable under paraphrasing — not just a nice-to-have, this is the mechanism the whole confidently-wrong-detection thread below depends on.

Real bugs found and fixed, in order:
1. **Anchor-text-discarding bug**: `protect_links_for_translation` was replacing the WHOLE `[anchor](url)` markdown link with a bare prime-number placeholder, discarding real anchor text — a comment that was mostly one link collapsed to an isolated number, causing MarianMT to hallucinate unrelated content. Fixed to protect only the URL, keep anchor text as prose.
2. **Link-density-dependent survival**: link/entity placeholder primes were being silently dropped by MarianMT at a rate that scaled with how many were packed into one translation call (8/8 lost on the worst-case row in the original whole-comment approach). Fixed via paragraph-level chunking (sentence-level fallback for any paragraph with >3 links), each chunk translated independently and reassembled in original order — this also directly resolves the "pure link-dump comment" case for free, since it naturally splits into small single-link paragraphs.
3. **Greedy decoding silently dropping content**: found a real case where greedy decoding dropped an entire opening sentence ("Watergate changed the country.") from a 6-sentence comment; beam search (num_beams=4) recovered it. Reproducibility doesn't require determinism here — Nash's call, since publishing the generated paraphrase set + method is what other researchers need to verify, not bit-exact regeneration — so beam search over greedy was a free choice, not a tradeoff.
4. **Proper-noun/acronym corruption**: even with beam search, back-translation corrupts names/acronyms ("KKK"→"CCC", "Catherine Austin Fitts"→"Katherin austin fitt's"). Tried general spaCy NER protection first — over-fired on this corpus's conspiracy-topic vocabulary (NIH/FDA/PCR/dates all tagged ORG/etc, hollowing whole sentences into strings of digits, worse than the word-substitution approach this project moved away from earlier). Narrowed to protecting ONLY the row's own known `target_entity` (case-insensitive) — the one thing that actually matters for training-label integrity; corrupting a non-target entity is low-stakes phrasing drift by comparison. `protect_entities_for_translation()` in `clean_reddit_markdown.py`, reuses the same prime-placeholder mechanism as links (extended pool, 60 primes total, shared allocation so link/entity primes never collide).
5. **Genuine near-OOM crashes on local MPS, THREE separate times** — the real infra story of this thread, worth reading carefully since it recurred despite escalating fixes:
   - First: `top`'s real memory footprint (RSIZE ~10GB) badly undercounted by `ps`'s RSS column (~100MB) — a real Activity-Monitor-vs-`ps` discrepancy on this Apple Silicon MPS setup, not a red herring. Root cause: PyTorch's MPS allocator cache growing unbounded across ~1,371 batches in the translation loop, `torch.mps.empty_cache()` only ever called once between the two model-load stages, never inside the per-batch loop.
   - Fix attempt 1 (clear every 20 batches): looked fine on a 60-batch test, still grew to 7GB+ over the real ~1,371-batch run.
   - Fix attempt 2 (`gc.collect()` + clear every batch): held flat in an 18-minute, 300+ batch stress test with real corpus data — then STILL hit 9.4GB on the actual full run. The stress test just hadn't run long enough to catch a slower climb.
   - Root cause, finally isolated directly (not guessed): a single near-max-length batch (8×768 tokens, beam=4) alone jumps memory ~1.4GB in one `generate()` call — this isn't a leak so much as genuinely large peak-per-batch memory for long sequences, and `empty_cache()`/`gc.collect()` don't reliably reclaim 100% of that peak on MPS, so the high-water mark ratchets up over many batches, especially when several long ones cluster together.
   - Actual fix: `batch_size=4`, `max_length=512` (matches MarianMT's real architectural position-embedding capacity anyway — content beyond ~512 tokens was already unreliable pre-truncation, so this cost nothing in quality). Verified against real corpus data plateauing at ~3GB across an 18-minute test — but this STILL failed at true full-corpus scale (9.4GB, safety-killed again).
   - **Final resolution: moved off MPS entirely, onto the VM's CUDA GPU** (`vm2image-20260810-093317`, L4, 23GB dedicated VRAM, not shared unified memory the way MPS is). A local CPU-only test was also tried as an intermediate step (memory rock-solid ~750MB, but 3+ hour ETA extrapolated — too slow) before landing on the VM as genuinely the better choice on both axes (speed AND memory safety), not just the safety-motivated fallback it started as.
   - A hard safety-kill monitor (bash loop polling `top`'s real MEM column, kill above a threshold) was used throughout this debugging as a backstop — caught every one of the three near-misses before an actual crash. Worth reusing this pattern for any future long-running local MPS job on this machine.
6. **Quality-gate + drop-on-lost-placeholder**: any row where a link OR the target_entity placeholder didn't survive the round-trip gets dropped from the output entirely (not silently kept with a corrupted label) — found one real case even after all the above fixes (the target_entity itself, "Bill Gates," silently dropped from a dense mid-sentence position, adjacent to another rare all-caps token "JEFFREY EPSTEIN" — likely beam search sacrificing an isolated low-probability numeric token for a smoother-sounding continuation). Additionally, similarity < 0.85 (all-MiniLM-L6-v2 cosine) rows are dropped.

**Final full-corpus result** (`outputs/reinfer_probs/paraphrase_backtranslation_full.csv`, run on VM): 3,582 human-labeled rows → 3,198 attempted (381 excluded as too-thin/link-heavy) → 94 dropped (placeholder loss) → 265 dropped (below similarity gate) → **2,839 final rows, mean similarity 0.951**.

## 2. Confidently-wrong detection — the actual diagnostic, several real course-corrections along the way

**The core question** (Nash's framing, corrected mine several times): not "does paraphrasing change predictions" in general (that conflates fragility with genuine ambiguity) and not hostile-vs-endorsement polarity flips (already solid, ~0.71-0.74 kappa, established and re-confirmed, not the problem). The actual target: **the other-vs-stance gate** — historically the project's persistent weak point (kappa 0.22-0.37 across every intervention tried) — specifically cases where the model is **confidently wrong**, not just uncertain (uncertain rows are self-flagging via the confidence score itself; confidently-wrong rows have no natural detection mechanism, which is the whole reason this thread exists).

**Real methodological correction mid-thread** (important, don't repeat this mistake): an early version of this check used the model's own predictions on train-split rows as a "ground truth" filter (only count a paraphrase-flip if the original was ALSO predicted correctly first) — Nash caught that this doesn't make sense for training data. The label is given/fixed supervision the model was directly optimized against; it's not something the model "discovers" or can be diagnostically "wrong" about on the original text in any causally-informative sense. The real signal is simply: does a meaning-preserving rewording of a known-labeled row still get predicted correctly? If not, that mismatch IS the failure, independent of what happened to the unparaphrased original. (There's a real, separate reason the original text CAN still show high confidence-toward-wrong even on training data, though: "other" rows only ever receive a confidence-suppression loss during training — `ConfidenceTrainer.compute_loss` in `train_binary_confidence.py`, `OTHER_CONF_LAMBDA=0.15` — never a classification loss, since there's no valid polarity target for them. The classifier logits head gets zero gradient signal about what an "other" row should map to, so it's free to be biased by whatever polar-sounding vocabulary is present, with only a soft, low-weight counterpressure on the confidence head specifically. This is a real, structural reason a meaningful fraction of "other" training rows can still show moderate-to-high self-confidence even on text the model has literally seen with the correct label — confirmed directly on 47 real train rows with orig_confidence 0.50-0.95, not a leak or a bug.)

**Numbers, using binconf_other015 alone** (the single confidence-head checkpoint — NOT the project's actual best result, see §4):
- Train-split, full 771 human-labeled "other" rows (not the 526-row paraphrase-pipeline-filtered subset used in an earlier pass — that filtered subset undercounts by excluding thin-comment/too-many-links rows before any inference ran on them at all): **58/771 = 7.5%** confidently (≥0.7) gated as stanced on ORIGINAL text alone.
- Val-split, full 175 human-labeled "other" rows: **48/175 = 27.4%** confidently gated as stanced on original text alone.
- **This train-vs-val gap is real and highly statistically significant**, not sampling noise: Fisher's exact test p=9.39e-12 (two-proportion z-test p=4.82e-14) on the clean, apples-to-apples original-text-only, fully-unfiltered comparison above. Worth investigating WHY train and val "other" rows differ this much in confidently-wrong rate before assuming it's just population variance — not yet investigated.
- The 48 val false positives are NOT boundary cases: mean confidence 0.872, median 0.893, half above 0.90.
- Combining original-text AND paraphrase-text checks on train (526-row filtered subset, both directions): 76/526 rows confidently wrong on original OR paraphrase (≥0.7) — of these, 41 were wrong on BOTH (a persistent, phrasing-independent content-level blind spot, not a paraphrasing-fragility artifact) vs 14 original-only vs 21 paraphrase-only. The "wrong on both" majority is the more important finding — it means the earlier working hypothesis (entity mentioned but not the grammatical/rhetorical target of evaluation — comparisons, reported-speech, hypotheticals) only explains part of the pattern; a bigger, more robust driver looks like raw density of conspiracy-topic vocabulary ("disinfo agent," "cover-up," "MK Ultra," "playbook") overwhelming whatever structural signal the classifier is supposed to use, independent of whether the sentence is actually evaluative.
- Val contributed an additional 43 confidently-wrong examples via paraphrase text specifically (used the paraphrase, not original val text, for these — Nash's framing: a meaning-preserving rewrite isn't literally training on val, though using it downstream to retrain the base classifier and re-evaluate on val would be a softer, real leakage path worth remembering if that's ever done).

### 8.1 Real bug found and fixed in the false-positive detector's negative class

The detector in §3 (AUC 0.859, 549/2131 flagged) had a real methodological flaw: its negative class was sourced ONLY from confident-correct POLAR rows — it never saw a single genuine, correctly-classified "other" row. Applied at true full scale (all 42,183 train rows, both human and machine-labeled — never attempted before this session), it flagged **94.6% of every "other"-labeled row** as a false positive. Not because that many are mislabeled — the detector had only learned "does this look like a confident polar prediction," and real "other" rows structurally never do, correct or not.

**Fixed**: `src/train_false_positive_detector.py` now sources negatives from TWO pools — confident-correct polar rows AND confident-correct "other" rows (confidence < 0.3), balanced 1:1:1 against the 119 positives. New CV: AUC **0.823** (down from the misleadingly-high 0.859 — expected, it's now solving the real, harder discrimination problem instead of a shortcut). Full 42,183-row rescan with the corrected detector: **31.6% flagged (13,337 rows)**, with a roughly even split across hostile (33.1%)/endorsement (29.7%)/other (31.8%) — a real sign it's learned an actual pattern, not a class proxy.

**Provenance breakdown of the flagged rows is the most useful finding here**: frontier/LLM-judge-scored batches (`frontier_random_expansion`, `frontier_boundary_expansion`) flag at ~47-51%, vs ~20% for ensemble-silver rows and mostly single-digit-to-20s% for human-labeled batches. Random-sampled frontier rows and deliberately-hardest boundary-sampled frontier rows flag at nearly the same rate (46.9% vs 51.0%) — ruling out "the frontier batches just happened to get harder cases" as the main explanation; points at something systemic in the frontier-judge labeling method itself. **Important caveat, verified not assumed**: checked whether the flag actually reflects binconf disagreeing with the frontier label — only **17.6%** of flagged frontier rows have an actual binconf-vs-label disagreement; the other 82.4% are flagged purely on embedding-pattern resemblance to known-error text, with binconf agreeing with the frontier label. So the flag is NOT primarily "binconf catches a frontier mistake" — for most flagged frontier rows there's no disagreement to adjudicate at all. What it actually tests is whether the *frontier label itself* is right on content that resembles past error cases — genuinely open, not something the flag rate alone can resolve. The cross-LLM agreement finding from earlier in this project (independent LLMs correlating reasonably well with each other) is a real reason not to assume "frontier label wrong" as the default read.

Stratified spot-check queue built and **wired into `hitl_rater.py`** (auto-discovery requires `id`+`full_text` columns — the first save didn't have them, fixed): `data/hitl/queue_fp_detector_spotcheck_r1.csv`, queue key `fp_detector_spotcheck_r1`, 60 rows, 5 per (provenance × label) cell across 4 provenance buckets (human/ensemble_silver/frontier_llm/other_queue) × 3 labels. ### 8.4 Hand-coded false-positive failure-mode taxonomy (all 76, not a sample)

Every one of the 76 known confidently-wrong "other" rows was read and categorized by hand (not automated), since the set is small enough. Real, distinguishable buckets (not mutually exclusive):
- **Comparison/tangential mention** (~23/76) — entity named only as a comparison point or incidental biographical detail, not actually being evaluated.
- **Narrative/event retelling** (~14/76) — pure factual description, no evaluative language toward the entity at all.
- **Genuinely ambivalent/mixed** (~14/76) — real hedged content, both praise and criticism present; arguably legitimately "other," not a clean classifier failure.
- **Reported belief** (~4/76) — describing a THIRD PARTY's view, not the author's own.
- **Meta-commentary about an article/source** (~5/76) — evaluating the source, not the entity.
- **Hypothetical/rhetorical, no stance asserted** (~5/76).
- **Possible human-label noise** (~7/76) — reads like genuine stance content; questionable whether "other" was even the correct human label, not necessarily a classifier failure.

**Comparison + narrative-retelling together account for over half (~37/76)** — the dominant failure mode is the entity being structurally present without being the actual grammatical/rhetorical subject of evaluation, not general ambiguity. This directly motivated §8.5.

### 8.5 Aboutness/entity-salience gate — validated as a real signal, ABSA integration blocked

Nash's proposal: instead of framing the stage1 gate purely as valence (other-vs-stanced), add a genuinely separate **aboutness gate** ("is this comment actually about the entity, or just mentioning it") ahead of it — directly targets the §8.4 dominant failure mode. Grounded in real NLP literature, not invented from scratch: **entity salience** (Dunietz & Gillick 2014; Gamon et al. 2013), **Centering Theory** (Grosz/Joshi/Weinstein 1995 — backward-looking center ranked by grammatical role), **entity grids** (Barzilay & Lapata 2008), and most directly transferable, **Aspect-Based Sentiment Analysis (ABSA)** — a mature subfield that explicitly splits "aspect/target extraction" from "sentiment toward that target," structurally the same two-gate architecture being proposed here, with existing datasets/tooling rather than pure theory.

**Two-tier heuristic test, validated with real (if moderate) signal**: (1) locate the sentence with the strongest evaluative language anywhere in the WHOLE comment (VADER sentiment, deterministic, no API calls) — not assumed to be the entity's own local sentence; (2) check whether the target entity co-occurs with that sentence, and whether it (or its dependency-chain ancestor) is the grammatical subject there (spaCy dependency parse). Real separation found between known false positives and true positives: entity co-occurs with the evaluative sentence 33.3% (FP) vs 45.3% (TP); is the subject of it 12.7% (FP) vs 20.3% (TP) — consistent direction across all three measures tested, ~12pp gap on the strongest one, on a 70-vs-74-row comparison. A cruder single-sentence-only version of this heuristic (just look at the entity's own local sentence, ignore where the evaluative language actually is) was flat/non-discriminating — the two-tier refinement is what makes it work. Script lives only in the session scratchpad (`/private/tmp/.../scratchpad/test_aboutness_hierarchical.py`), not yet promoted to `src/` — do that before building further on it.

**PyABSA investigated as an off-the-shelf ABSA tool, genuinely blocked, not abandoned by choice**: installed cleanly (`pip install pyabsa`, actively maintained package), but its pretrained multilingual APC checkpoint (2023-era, `fast_lcf_bert`) crashes loading against the currently-installed `transformers` version — a tokenizer API change (`DebertaV2TokenizerFast` no longer exposes `special_tokens_map` the way the old checkpoint-loading code expects). Real external compatibility rot, not a quick fix — pinning an old `transformers` risks breaking everything else that already depends on the current version in this environment. Next step if pursued: either pin transformers in an isolated env just for PyABSA, look for an updated checkpoint, or fine-tune PyABSA's APC architecture fresh on this project's own (text, target_entity, label) data instead of using the broken pretrained review-domain checkpoint zero-shot.
